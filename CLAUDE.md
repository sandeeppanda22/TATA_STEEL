# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Tata Steel Road Programme (Phase 1: 17 roads) progress dashboard. The current app is `dashboard/` — FastAPI + PostgreSQL (`tata_road` schema) + a plain HTML/JS/CSS front end. **The database is the source of truth**: roads, activities and progress are entered and edited in the app; nothing reads Excel at runtime. (The initial 17 roads were bulk-loaded once from `Source/*.xlsx` — see the Pipeline note below — and that loader is now optional.) Business rules are in `docs/01_business_rules.md` (BR-xx confirmed, OPEN-xx unruled) and are cited throughout the code — read them before changing any calculation. Longer write-up: `docs/PROJECT_DOCUMENTATION.md`.

An earlier stdlib/SQLite app still sits in the repo root (`server.py`, `index.html`, `calc.py`, `plan.csv`, `bottlenecks.csv`, `roadworks.db`) plus the legacy Tkinter app (`roadworks.py`, `build_exe.bat`). They are separate from `dashboard/` and share no code or data with it; treat them as legacy/reference unless asked. **Feature parity check (2026-10-13):** `dashboard/` now also covers the legacy app's manual bottleneck records (`manual_issue` table, `/api/db/manual-bottlenecks` CRUD), bulk weekly-progress CSV import (`POST /api/db/weekly/import-csv`, all-or-nothing, appends ledger rows), and CSV export of progress history / summary (`GET /api/db/export/weekly-history`, `GET /api/db/export/summary`) — the three gaps found when the legacy app was audited for retirement.

## Commands

- Full rebuild (DB + deps check + seed regen + verify; does **not** start the server): `./rebuild.sh`. `rebuild.sh` also runs `db/06_alter_activity_unique.sql` and `db/05_live_change.sql`. Incremental: `db/00_schema.sql` uses `CREATE SCHEMA/TABLE/INDEX IF NOT EXISTS` and `scripts/gen_seed.py` emits `ON CONFLICT DO NOTHING`, so re-running it only adds roads/activities/issues that are new in `Source/*.xlsx` — it never drops the schema or touches an existing row (weekly actuals, edits, and any UI-added road all survive). Flags via env: `FORCE=1` (load even if `scripts/verify_seed.py` fails), `PORT=`.
- Read-only DB health check: `./03_validate.sh` (tables, counts 17/177/10, orphans, Monday weeks, BR-05 totals; uses `DATABASE_URL` if set, else local `PG*`; exit 1 only on hard failures — road 10=130 is a WARN). `./02_build.sh` is just a wrapper that `exec`s `./rebuild.sh`. `db/create_database.sql` (one-time, run against the `postgres` maintenance DB) creates the `tata_steel` database on a self-managed server.
- Render deploy (long-lived uvicorn, `render.yaml` Blueprint): build command `bash render_build.sh` installs deps and, **only if `ALLOW_DB_BOOTSTRAP=yes`** (safety lock; `sync: false` in `render.yaml` so the dashboard value is authoritative; unset = locked; build log prints the received value) and `DATABASE_URL` is set and `psql` exists, applies `db/00_schema.sql` (IF NOT EXISTS only → adds missing tables, never alters existing ones) and `db/01_seed.sql` only when `road` is empty (changed columns/seed rows on existing tables are not picked up). Start: `uvicorn dashboard.main:app --host 0.0.0.0 --port $PORT`. See `docs/DEPLOY_RENDER.md`.
- Vercel deploy: `api/index.py` re-exports `dashboard.main.app`, `vercel.json` rewrites all paths to it, DB via `DATABASE_URL` (Neon); Vercel never runs `rebuild.sh` — seed Neon by hand, see `docs/DEPLOY_VERCEL.md`.
- Run server: `python3 -m uvicorn dashboard.main:app --reload --host 0.0.0.0 --port 8000` (or `run.bat` on Windows).
- Pre-flight only: `python3 scripts/verify_seed.py`. Dataset summary: `python3 scripts/build_data.py`. Regenerate seed: `cd scripts && python3 gen_seed.py`.
- Deps: `pip install -r requirements.txt` (fastapi, uvicorn, openpyxl, psycopg2-binary). No venv, no linter. Tests: `python3 -m unittest discover -s tests`, `node --test tests/`.
- DB connection: `DATABASE_URL`, else `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` (defaults port 5432, user `postgres`, db `tata_steel`, **no default host** → Unix socket, avoids a GSSAPI/Kerberos failure on this machine). `dashboard/db.py` also loads a gitignored repo-root `.env` that `rebuild.sh` writes.

## Architecture

- Optional bulk loader (legacy): `Source/*.xlsx` → `scripts/build_data.py` (in memory) → `scripts/gen_seed.py` → `db/01_seed.sql` → Postgres, incrementally (`ON CONFLICT DO NOTHING` on `road(road_no)`, `activity(road_no, raw_name)`, and a `data_issue` dedup index). `scripts/config.py` holds the canonical activity sequence (BR-03), major weights (BR-04), raw-name→canonical map and `road_weightage()` (BR-05).
- A road can also be added directly through the dashboard (`POST /api/db/roads`, "Add Road" button on the Roads tab) with its own activities, start/end dates — no Excel edit or rebuild needed. It is stamped `source_file = 'manual-entry'` and, because the rebuild is incremental, is never erased by a later `./rebuild.sh`.
- `dashboard/main.py` mounts only the `/api/db/*` router (`dashboard/db_routes.py`) and the static front end (`dashboard/static/`, served with `no-cache`). There is no JSON/static data tier any more.
- `dashboard/calculations.py` holds all metrics (road/overall %, vendor/LM performance, bottlenecks, CPM, milestones, chart data). Metrics are computed **only server-side** here; `dashboard.js` renders what the API returns (apart from the fixed `ACTIVITY_SEQUENCE`/`MAJOR_WEIGHTS` display constants mirrored from `scripts/config.py` — change both).
- `weekly_entry` is an **append-only ledger** (ruling 2026-10-13): `actual_qty` is that submission's quantity (a delta), every POST/CSV-import row is its own `INSERT` that **adds** to the cumulative (`SUM(actual_qty)`), and there is no `UNIQUE (activity_id, week_start_date)` in `00_schema.sql` any more. Each row still carries its Monday–Sunday `week_start_date` (`submit_weekly_entry` snaps any date to its Monday). `DELETE /activities/{id}/weekly/{entry_id}` removes one row by `entry_id`. Caveat: `CREATE TABLE IF NOT EXISTS` never alters an existing DB, so one created before this change still has the old UNIQUE and, with the plain `INSERT`, rejects a second entry in the same week until the constraint is dropped by hand. (The legacy SQLite app stores cumulative instead — don't mix them up.)
- Displayed activity/road/bottleneck % is capped at 100; `road_progress()` returns `(road_pct, drain_pct, over_planned_count)` and the API/UI flag `over_planned` where actual > planned_qty.
- BR-08 gating was **removed** (ruling 2026-10-13): progress may be entered for any activity in any order. `calculations.check_gating` is gone; `db_routes._validate_gating` is a no-op stub with no callers. Don't re-add checks without a new ruling.
- Edits to `road`/`activity` go through `PUT` routes and are logged field-by-field in `edit_log`. There is no confirmation step for any field (the old source-override 409 was removed); `edit_log.source_override` is a legacy column that is no longer written or shown.
- All SQL uses unqualified table names; `db.get_conn()` is a context manager that borrows from a lazily-created `ThreadedConnectionPool` (1–8 conns) and runs `SET search_path TO tata_road, public` on every checkout (not as a libpq `options` startup parameter — Neon's pooled PgBouncer endpoint rejects that). It does not commit: `execute*` commit explicitly, and the connection goes back to the pool in `finally`.

- **Live refresh feed.** `db/05_live_change.sql` (idempotent; run by `rebuild.sh` and, when unlocked, `render_build.sh`) adds `live_change_seq`, `live_change_marker` and a statement-level `trg_live_change_marker` trigger on `road, activity, weekly_entry, data_issue, edit_log, manual_issue`. `GET /api/db/live/changes` (60/min per client IP — there is no login) returns one `change_seq` per table in `live_feed.LIVE_FEED_TABLES` (must equal the SQL list; `tests/test_live_feed.py` checks). `static/live-refresh.js` polls it and `dashboard.js` (`LIVE_TABLE_TABS`) reloads only the affected tabs; busy forms get a "new updates" banner instead. Existing DBs need `05_live_change.sql` applied once (Neon/Render: by hand or one build with `ALLOW_DB_BOOTSTRAP=yes`); until then the feed reports `enabled:false` and the header Reload button stays visible. Tests: `python3 -m unittest discover -s tests`, `node --test tests/`.

- **Road issues (hindrance windows).** `road_issue` table (in `00_schema.sql`) + `POST/GET /api/db/roads/{n}/issues`, "Issue" button per road. Adding one (From/To, inclusive days = `shift_days`) shifts the road's unfinished activities later in one transaction: ended-before-From or fully-complete activities are untouched, activities starting on/after From move start+end, activities in progress across From move only their end; `road.start_date/end_date` follow the same rule. Every changed date is written to `edit_log` (road rows as source overrides). `road_issue_shift` records what each issue moved; `PUT`/`DELETE /roads/{n}/issues/{id}` first reverse it (subtract `shift_days` from current dates) and, for PUT, re-apply the new window. Issues created before `road_issue_shift` existed can't be reversed. UI notifications use `uiToast`/`uiConfirm` (dashboard.js), never native `alert`/`confirm`. Existing DBs need `00_schema.sql` (adds the two tables only) and `05_live_change.sql` (re-run, adds the trigger) applied once. Test: `tests/test_road_issue.py`.

- **Phase groups.** Roads tab sections are built from the distinct `road.phase` values (`phaseSection` in `dashboard.js`, collapsed state in `localStorage` key `tata_phase_collapsed`); nothing is hard-coded to Phase 1, and `GET /roads` returns `phase`.
- **Shared code, don't re-copy.** Percent complete is `calculations.activity_pct(done, planned, cap=)` (use it, don't re-write `done/planned*100`); end-before-start checks go through `db_routes._check_date_order`; Performance / Backlog / Targets tables are column lists (`PERF_COLS`, `BACKLOG_COLS`, `TARGET_COLS`, `ACT_COLS`) rendered by `expandableTable` / `roadBlock` / `summaryRowHtml` in `dashboard.js` (the group print reuses the same columns); dates use `toISO`. `tests/test_calculations.py` pins the metric outputs against `tests/calc_golden.json` — regenerate only on a deliberate behaviour change (`python3 tests/test_calculations.py --regen`).
- **Dropdown + "add new" fields.** Vendor, Line Manager, Road Type and Phase in both Add Road and Edit Road use the shared `comboFieldHtml` / `comboCheck` / `comboValue` / `wireComboForm` (`ROAD_COMBOS` lists the fields); don't write a second copy for another form.
- **Summary rows & printing.** Performance, Backlog and Targets group rows are selectable (`wireSelectableRows`) and expand to road-wise detail (`/performance/vendor|line-manager`, `/performance/backlog?detail=true`, `/performance/target` all return `road_rows`). Each Backlog/Targets row has a **Print** button that prints one group through a temporary `#printSheet` (body class `printing-single`, TATA STEEL banner); the header Print / Export still prints the whole tab.

## Gotchas

- **Date format is layered, and the layer decides.** Dates travel as ISO `YYYY-MM-DD` through the DB, the seed, and every API JSON payload (machine format: unambiguous, sortable) and are rendered as **DD-MM-YYYY** only where a human reads them. In the browser that conversion is `fmtDate()`/`fmtDateTime()` in `dashboard.js` — so API routes feeding the UI should keep returning `.isoformat()` and must NOT pre-format. The trap: any **human-read surface that bypasses `dashboard.js`** has to convert server-side itself — exported files (`_fmt_date_ddmmyyyy()` for text/CSV; a real `date` value plus `number_format = "DD-MM-YYYY"` in `_xlsx_response`, so Excel displays DD-MM-YYYY while still sorting as a date) and human-readable prose built in Python (`calculations.critical_path`'s overlap `note` uses `strftime('%d-%m-%Y')`). Writing `.isoformat()` into an export or a prose string is the recurring bug.
- Exported column headers use the **UI wording**, not db/API field names — the `_SUMMARY_LABELS` / `_ROAD_LABELS` maps in `db_routes.py` mirror the picker labels in `dashboard.js`; change both.
- `./rebuild.sh` is incremental and never drops the schema or discards entered data — see Architecture above. The DB tier has never been run end-to-end against a live Postgres per `docs/02_build_and_rebuild.md`.
- Known unresolved data defect: road 10 maps two rows (`Paver Laying`, `RCC`) to the `Road` major → weights total 130, so `verify_seed.py` fails and `rebuild.sh` stops unless `FORCE=1`. Needs a user ruling (see `docs/02_build_and_rebuild.md` §0).
- Bare `RCC` row means the ROAD major on RCC roads but an RCC Drain on Paver roads (`config.normalize`, `road_type` dependent).
- `Source/` is untracked/changed in git: the workbook is now `Final Sheet for Claude Project-Phase-1.xlsx`; every `.xlsx` in `Source/` is read (BR-13).
- Weekly-entry code/schema changes (ledger, gating removal) are uncommitted on `develop` as of 2026-10-13 (`dashboard/*`, `db/00_schema.sql`, `docs/01_business_rules.md`).
- `db/04_restore.sql` is re-runnable: weekly rows restore with a `NOT EXISTS` anti-join on `(activity_id, week_start_date, entered_at, actual_qty)` and `edit_log` rows on their content + `edited_at` (`IS NOT DISTINCT FROM` for the nullable values). It no longer uses `ON CONFLICT (activity_id, week_start_date)` — that needed the removed UNIQUE and errored on a current schema.
- Stale docstring: `import_weekly_csv` (`db_routes.py`) still says "BR-08 gating is enforced per row"; the code does no gating.
- Stray files in the root (`clipboard_image_*.jpg`, `_write_test.md`, `_diag_gsb.py`, `roadworks.db.bak-*`, `__pycache__/`) are scratch/leftovers, not part of the app.
- Back up the DB before schema or bulk-data changes.
- `db/03_backup.sql` / `db/04_restore.sql` are no longer called by `rebuild.sh` (the old `KEEP=1` backup/restore dance is obsolete now that rebuilds are incremental) — left in place as a manual safety-backup option, not part of the normal flow.
